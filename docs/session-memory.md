# Textract — Session Memory

## Project Identity
Fork of [simonsanchezart/textract](https://github.com/simonsanchezart/textract) (MIT, 292 stars) — a Tauri v2 desktop app that extracts/deskews textures from photos via 4-corner perspective warp. Our fork: `ghsnyc/textract`. Goals: (1) native macOS support, (2) a private signed installer for personal machines, (3) a new curved-surface (mesh-warp) extraction feature, (4) upstream PRs for both.

Stack: React 19 + TypeScript + Vite + Tailwind + Zustand + react-konva (frontend) / Rust + Tauri v2 + image/imageproc/rayon (backend, `src-tauri/`).

## How to test the curved-surface (grid mark) feature
1. `cd textract && CARGO_TARGET_DIR="/Volumes/Studio 4TB T500/_Caches/CodingBUILD_Cache/textract-dev/target" npm run tauri dev`
2. Load a photo with an actual curved surface (bottle label, bent sign, etc.)
3. Click the new 3x3-grid toolbar icon (top-left, next to Load/Convert) or press Shift+G to switch to grid mode — icon highlights when active
4. Cmd+Click (macOS) or Ctrl+Click (Windows/Linux) 4 corners around the curved region, same gesture as a normal (quad) mark — this seeds a straight 4x4 interior grid
5. Drag the interior grid points (not just corners) to trace the actual curve in the photo
6. Shift+R or the Convert toolbar button to extract — should produce a flattened rectangle on the right (export) canvas
7. Shift+G back to quad mode for normal marks

## Key Technical Decisions
- Curved-surface warp approach: piecewise-affine / Delaunay-triangulated mesh warp over an NxM point grid (not full thin-plate-spline) — simpler, uses primitives already available via `imageproc`/hand-rolled barycentric warps, and `imageproc::geometric_transformations::Projection` is retained unchanged for the existing 4-point path.
- New mesh-warp feature is additive: new Tauri command (e.g. `transform_image_mesh`) alongside existing `transform_image`, not a replacement.
- Personal installer: arm64-only (this machine + user's other machines are all Apple Silicon), signed with `Developer ID Application: Glenn Hernandez Studios Incorporated`, kept private — not published anywhere.
- Rust installed via standard global rustup (`~/.cargo`, `~/.rustup`), not project-local — user's explicit choice after weighing self-containment vs reusability.

### 2026-08-07 — Session 6: bezier right-click convert (real root cause found), Atlas canvas undo/redo
- **Right-click convert saga concluded (pending final user confirmation)**: after 3 prior fix attempts across sessions 5 and this one (missing Konva `closed` prop; missing `id` on draggable points) still didn't work, and the user reported a new clue (hover tint clearing on right-click) plus zero diagnostic output from the previous round's added logging, spawned an Opus agent that **reproduced the bug live in a real browser** — ran the app's own Vite dev server standalone, stubbed just enough of `window.__TAURI_INTERNALS__` to get past the top-level crash (`<Navbar>` calls a Tauri API on mount), and dispatched real right-click sequences with a measured before/after table. Actual root cause: the context-menu's "Convert Hovered"/"Remove Mark" items were gated on `hoverShape instanceof Konva.Line`, but the 12 draggable corner/handle points are `Konva.Rect`s layered on top of the outline — a right-click landing on a point (far more likely with 12 points than a quad's 4) resolved `hoverShape` to a `Rect`, failed the `instanceof` check, and rendered **neither menu item at all**, which is why no diagnostic ever fired: there was nothing to click. Fixed by resolving `hoverShape.id()` against the mark store instead of the shape's class; same latent bug existed in "Remove Mark" via `hoverShape.getAttr("removeMark")` (only exists on the outline). Added a permanent hit-test diagnostic breadcrumb. The hover-tint-clearing clue turned out to be expected Radix `DismissableLayer` behavior (sets `pointer-events: none` on body → real `pointerleave`), unrelated to the actual bug. See `LEARNINGS.md` for the generalizable pattern and the browser-harness debugging technique.
- **Atlas canvas undo/redo**, requested earlier and explicitly deferred, built this session: same zundo `temporal` wrapping pattern as the Mark canvas's existing undo (leading-edge debounced `handleSet` for the same reason — a transform gesture fires 3 separate `set()` calls). `Toolbar.tsx` gained a `position` prop (`"top-left"` default, new `"top-right"`) so a second button group renders per canvas; both canvases now show visible Undo/Redo buttons (Mark's undo was previously keyboard-only). User asked to confirm the two canvases' undo/redo can't cross-contaminate — confirmed by construction (separate zundo instances, separate per-canvas focus containers), no code change needed, just an explanation.
- User's process question: once Atlas undo/redo is confirmed, it goes back to upstream **PR #19** (`pr/undo-redo`) as additional commits on the same PR, not a new PR — same feature area, and PR #19 is already retargeted to the maintainer's new `dev` branch (see below).
- **Upstream workflow change**: the maintainer created a `dev` branch specifically for PRs needing more iteration before `main`, and asked for all open PRs retargeted there. Done same day for #18-#21 via `gh pr edit <n> --base dev`. Local tracking split into a dedicated `textract-tracking` worktree (never used for testing) after a near-miss where checking out `dev` directly in the actively-tested `textract/` folder swapped its working tree out from under a live test session.

### 2026-08-06/07 — Session 5: curve/tension bugs fixed, then replaced with a Bezier-boundary tool
- Curve/tension (from session 4's deferred plan item) shipped, then hit two real bugs on the user's first hands-on test: the dirty flag wasn't set after pressing `S`/adjusting tension, so Convert silently skipped edited marks; and the per-cell "all 4 corners must be smooth" eligibility rule was structurally unusable (marking an interior region smooth always required touching the mark's real outer corners too, defeating the point of keeping corners sharp). Both fixed — the second via an Opus redesign to per-direction/per-segment tension (a run between two points curves only if both its own endpoints are smooth, independent of the perpendicular direction), which is provably continuous (tension=1.0 is exactly linear) so there's no crease at a smooth/sharp boundary.
- **Separately found and fixed a real, unrelated bug while investigating**: `Canvas.tsx`'s keyboard-focus container was never actually given DOM focus anywhere in the codebase (confirmed via `grep -rn "\.focus()"` returning nothing), so canvas keyboard shortcuts only fired if some OTHER focusable element (e.g. a toolbar `<input>`) happened to already have focus — explains why shortcuts felt randomly unreliable. Fixed with an explicit `onMouseDown={() => containerRef.current?.focus()}`, benefiting every shortcut in the app, not just this feature.
- **User pushed back hard on the whole curve/tension approach after a real bottle-photo test still showed no visible curve**, and proposed a Photoshop-Warp-style Bezier-edge tool instead. Research (NotebookLM) confirmed Bezier boundary + Coons-patch/harmonic-extension interior fill is the standard technique for exactly this. Built as a **new, separate mark mode** (not a replacement — grid mode stays useful for box/linear shapes bent at the edges): 4 independent cubic-bezier edges, arc-length-parameterized sampling, Coons patch interior fill feeding the same triangulation backend the grid-mark path already used (refactored into a shared function, verified behavior-preserving against all 11 pre-existing tests before adding any bezier code).
- Two more real bugs found via hands-on testing on the finished bezier tool and fixed (Opus-reviewed both rounds): missing `closed` prop meant no fill was drawn at all (first right-click-convert attempt); no interior visual feedback / dim guide lines / non-working multi-select (all added, plus a one-frame drag snap-back bug Opus caught along the way). See Session 6 above for the eventual real root cause of right-click convert, which neither of these two rounds actually fixed.
- Also switched the tension-adjustment shortcut from `[`/`]` to `-`/`=` per user request (more intuitive/reachable), and fixed the "S and -/= write junk state on bezier marks" gap flagged by the Opus review (those are grid-mark-only concepts).

### 2026-08-05 — Session 4: multi-select group-drag fix, help doc alignment fix, upstream PR split and open
- **User confirmed session 3's batch works**, plus reported two new bugs: (1) Shift+Click multi-select worked but dragging one of several selected points only moved that one point, not the group; (2) the bundled help doc's mac/windows shortcut columns visually collided.
- **Multi-select group-drag root cause**: `onMouseDown` unconditionally called `selectPoint` (replacing the whole selection) before a drag started, so grabbing any already-selected point collapsed the selection to just that point right before `onDragStart` fired. Fixed by only collapsing to single-select if the clicked point wasn't already part of the current selection; added a drag-start snapshot (`dragStartRef`) so `onDragMove`/`onDragEnd` can apply the same delta to every selected point, not just the one Konva reports drag events for.
- **Help doc alignment root cause**: `table-layout: auto` (the default) let each of the 3 shortcut tables independently compute column widths based on their own mix of `colspan`/3-column rows, so the macOS header drifted out of alignment with the shortcut pills below it. Fixed with `table-layout: fixed` + an explicit `<colgroup>` on all 3 tables.
- **Split `feature/macos-support` into 4 upstream PRs** per the maintainer's explicit one-PR-per-feature request: curved-surface mesh warp ([#18](https://github.com/simonsanchezart/textract/pull/18)), undo/redo ([#19](https://github.com/simonsanchezart/textract/pull/19)), mark-editing UX ([#20](https://github.com/simonsanchezart/textract/pull/20)), help doc ([#21](https://github.com/simonsanchezart/textract/pull/21)). Used 4 isolated `git worktree`s, cherry-picking commits per-feature onto fresh branches off `upstream/main`. Required real surgery during conflict resolution to keep each branch's diff scoped to its own feature (e.g. dropping grid-mode code that leaked into non-curved-surface branches via shared-file conflicts, moving a misplaced Undo/Redo tooltip line from the UX branch to the undo branch).
- **Opus review pass on all 4 branches before pushing** (user's explicit request: "use opus if it helps to make sure it's all done well") found zero leftover conflict markers and zero cross-PR contamination, but did catch two real issues: a stale code comment in the UX branch that called multi-select a "future feature" right next to the code implementing it, and two commit messages in the curved-surface branch that leaked fork-internal references (a PROGRESS.md mention, a fork-only commit hash) not meaningful upstream. Both fixed before push.

### 2026-08-05 — Session 3: Phase 4b bugs fixed and confirmed, new multi-select feature, compacting on context limit
- **Both bugs from session 2's cutoff, fixed and confirmed working live by the user**: point-drag undo (root cause: `Mark.tsx`'s local `points` React state never re-synced from the store — a plain React staleness bug, not another zundo issue) and the quad-mode icon/toolbar dimming. Found by re-reading code directly, no Opus needed for either.
- **Handle sizing bug**: user reported handles were "still tiny and not changeable" even after session 2's zoom-compensation fix. Decoupled entirely from image size; now `scaleFactor = markHandleScale / canvasZoom`, giving a sane ~20px default.

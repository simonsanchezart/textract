## Rust / Tauri / macOS

- **The app builds and runs natively on macOS with zero code changes.** `cargo check` / `npm run tauri dev` both succeed out of the box (Xcode 26.3, rustc 1.97.1, macOS 15.7.8, Apple Silicon). The Rust backend has no platform-specific code; the only reason macOS "isn't supported" upstream is missing bundle/CI config (see Phase 2).
- **Benign updater error in dev mode:** `[ERROR][webview] None of the fallback platforms ["darwin-aarch64-app", "darwin-aarch64"] were found in the response platforms object`. This is the `tauri-plugin-updater` checking `latest.json` on GitHub Releases, which (as expected) has no macOS entry since CI never built one. Not a real error — will resolve itself once macOS releases exist, or can be ignored entirely in dev.
- **Dev-mode window may open on a secondary monitor, and multi-display screenshot tooling can miss it.** On this 3-monitor setup, the Tauri window appeared on the monitor arranged *below* the primary display in global coordinate space (Y=1440+), not the primary. `screencapture -D <n>` display-index numbering did NOT match `CGDirectDisplayID` order — confirm actual window position via `CGWindowListCopyWindowInfo` (or the Swift one-liner below) before concluding a window failed to launch. Don't assume "nothing on any display capture" means the app crashed — check window existence via the window list APIs first.
  ```swift
  // /tmp/winlist.swift — list windows by owner name (bypasses accessibility/TCC restrictions)
  import CoreGraphics
  let list = CGWindowListCopyWindowInfo(.optionAll, kCGNullWindowID) as! [[String: AnyObject]]
  for w in list where (w["kCGWindowOwnerName"] as? String)?.lowercased().contains("textract") == true { print(w) }
  ```
  Then capture that specific window regardless of which monitor it's on: `screencapture -x -l <kCGWindowNumber> out.png` (note: `CGWindowListCreateImage` is removed as of macOS 15 — `screencapture -l` still works and uses ScreenCaptureKit internally).
- **`computer-use` MCP cannot target an unbundled dev binary.** `request_access` resolves app names against the LaunchServices index; a `cargo run`/`tauri dev` binary launched directly (no `.app` wrapper, no bundle ID) isn't registered there, so `request_access` returns "doesn't match any installed or running application" even though `lsappinfo`/`ps` show it as a live foreground GUI process. Interactive click-testing (drag corners, verify extraction) has to wait for a real `.app` bundle (Phase 2) — dev-mode verification is visual-only (screenshot the window) until then. Similarly, AppleScript/System Events `count of windows` on the process returns 0 without Accessibility (TCC) permission granted to the calling shell — don't mistake that for "no window exists"; cross-check with the CGWindowList approach above, which doesn't require any special permission.
- **Tauri v2 macOS signing/notarization is entirely env-var driven — no extra CLI flags needed.** Set `APPLE_SIGNING_IDENTITY="Developer ID Application: <Name> (<TEAM_ID>)"` before `npm run tauri build` and it signs both `.app` and `.dmg` with hardened runtime automatically. For notarization, Tauri looks for `APPLE_ID`+`APPLE_PASSWORD`+`APPLE_TEAM_ID` *or* `APPLE_API_KEY`+`APPLE_API_ISSUER`+`APPLE_API_KEY_PATH` env vars; without them it just prints `Warn skipping app notarization` and continues (not a failure). We instead notarized manually after the build via `xcrun notarytool submit ... --keychain-profile <name> --wait` + `xcrun stapler staple` on both the `.dmg` and the `.app` inside it — gives the same result without exporting a plaintext app-specific password into the build's env at all.
- **Check for an existing `xcrun notarytool` keychain profile before asking the user for new Apple credentials.** `xcrun notarytool store-credentials` persists to the login Keychain under a profile name; `xcrun notarytool history --keychain-profile "<name>"` succeeds silently if the profile already exists (no password re-entry). This user already had `"App-Notarization"` set up from prior Swift/macOS projects (see `swift-macos-menubar` skill, `GHS_Captions_AE_Extension`/`GHS_Text-to-Privacy` `scripts/build-pkg.sh`) — reused it instead of generating a new app-specific password. `security find-generic-password`/keychain dumps don't reliably surface notarytool profile names (they're not stored under a human-readable service string); grep sibling projects' release scripts for `--keychain-profile "<name>"` instead.
- **`Entitlements.plist` is required for hardened-runtime signing of a Tauri/WKWebView app**, or the notarized/hardened build can misbehave (WebKit needs JIT). Needed keys: `com.apple.security.cs.allow-jit`, `com.apple.security.cs.allow-unsigned-executable-memory`, `com.apple.security.cs.disable-library-validation` — set `bundle.macOS.entitlements` in `tauri.conf.json` to point at the file. Sourced from Tauri's own macOS signing docs via the NotebookLM notebook rather than guessing.
- **`spctl -a -vv` is the right one-command Gatekeeper check** — distinguishes `rejected / source=Unnotarized Developer ID` (signed but not notarized — still needs right-click→Open) from `accepted / source=Notarized Developer ID` (fully frictionless install) at a glance.
- **Network-drive build cache pattern confirmed necessary here too.** `npm install` directly on the SMB-mounted project (`/Volumes/gfxWorkDrive/...`) took ~20 minutes for 855 packages. For the Rust build, set `CARGO_TARGET_DIR` to a local disk cache (e.g. `/Volumes/Studio 4TB T500/_Caches/CodingBUILD_Cache/textract-dev/target`) instead of letting `target/` live on the network mount — cuts a from-scratch `cargo check` down to ~30s. Source stays on the network drive (edited normally); only the Rust build output needs to be local. Per the global CLAUDE.md build-cache rule, delete the cache folder when the project wraps up.

## Git / concurrent sessions

- **Don't `git checkout -b`/cherry-pick in a shared working tree if another session (e.g. a spawned background task) might be live-editing the same checkout.** Hit real file-content races here — `git cherry-pick` repeatedly failed with "local changes would be overwritten" for files that showed an empty `git diff` moments later, and `git cherry-pick --abort` itself failed ("Entry not uptodate") leaving the branch pointer stuck. Root cause: a separately spawned session (started via `spawn_task`) was editing files in the exact same `textract/` directory at the same time, not an isolated worktree as its own description implied. Recovery: `git checkout <known-good-branch>` (not `--abort`) to escape the stuck cherry-pick state, verify the original branch's commits are intact (they were — cherry-pick failures don't touch the source branch), then do the actual PR-prep surgery in a **separate `git worktree add ../<name> -b <branch> upstream/main`** so it has its own working directory and index, fully isolated from whatever the other session is doing. Cherry-picks that had failed 3 times in the shared tree succeeded on the first try in the isolated worktree.
- **`spawn_task`'s "start it in a fresh worktree with one click" language is not a guarantee** — verify independently (e.g. `git worktree list`, or just notice files changing underneath you) rather than assuming isolation.
- **The exact same "Your local changes... would be overwritten by merge" error also happens with zero concurrency, purely from network-drive flakiness during multi-step `git rebase -i`/`git cherry-pick` sequences.** Confirmed in a later session splitting one branch into 4 upstream PRs via isolated worktrees (no concurrent session this time, `git status` clean each time it happened): the error fired mid-rebase between successfully completing one step and starting the next, with the working tree provably clean (`git status --short` empty) at the moment of failure. It is not a real conflict — `git status` after the error shows the interactive rebase merely paused with the *next* step re-queued; running `git rebase --continue` (or `git cherry-pick --continue`) again immediately succeeds, and the final diff (`git diff --stat` against the target base) is byte-identical to a clean run. Root cause is almost certainly the same SMB-mount rapid-sequential-file-I/O issue documented in the global CLAUDE.md's "Build Cache for Network-Drive Projects" section, just triggered by git's internal working-tree checkout during rebase rather than by a build tool. Don't `--abort` reflexively when this happens — check `git status` first; if it's clean, just retry `--continue`. Plain `git push` (which mostly transfers packed objects, not individual working-tree files) was unaffected and fast even on the same network-drive repo.

## Zustand / zundo (undo-redo)

- **zundo's `handleSet` debounce/throttle MUST be leading-edge, not trailing-edge — this is not intuitive and got it wrong on the first pass.** zundo calls `handleSet(pastState, currentStateOrNull, ...)` with the state as it existed *before* the triggering `set()` call (confirmed by reading `zundo/dist/index.js`'s `curriedHandleSet`). A standard trailing-edge debounce (`clearTimeout; setTimeout(() => fn(...latestArgs), delay)`) keeps the *last* call's arguments in a burst — for a drag gesture that's the state from just before the very last pointer-move, i.e. almost the final position. Undo then "works" but restores to ~where the point already was, reading as a total no-op, and repeated undo presses walk back through unrelated history (other store actions) instead. Leading-edge (fire on the *first* call of a burst, ignore the rest until quiet) keeps the state from *before the whole gesture started*, which is what undo should actually restore to. Verify this kind of library-internal calling-convention assumption with a standalone reproduction script against the real store composition — don't just trust that `tsc`/lint passing means the semantics are right.
- **A single logical user action can fire multiple Zustand store `set()` calls**, and since `temporal` snapshots on every `set()` by default, that silently multiplies undo-stack entries per action. Concretely: `onDragEnd` in this codebase calls `updateMarkPoint(...)` then `updateMarkDirty(...)` as two separate action calls — two snapshots for one drag. Either coalesce via a debounced `handleSet`, or restructure the action into a single `set()` call if you control the store.
- **RESOLVED (was flagged above as not-yet-root-caused): point-drag undo not working while image-drag undo worked was NOT a zundo issue at all — it was a React local-state staleness bug.** `Mark.tsx` keeps a local `points` React state (`useState(mark.points)`), needed so `onDragMove` can give live visual feedback before a drag commits to the store on drag-end. It was only ever seeded from the `mark.points` prop once at mount, with no `useEffect` re-syncing it — so undo correctly reverted the *store*, but the component kept rendering its stale local copy. `MarkImage.tsx`'s image position, by contrast, renders directly from the `imageData.position` prop every render (no local shadow copy), which is why it worked. **General lesson: when a "shared state that also needs local optimistic/in-progress state" component doesn't visually reflect a store change, check for exactly this pattern before assuming the store/history logic itself is broken** — the store can be 100% correct while the view layer silently ignores it.

## React-Konva

- **A Konva node's synthetic `click` event bubbles up through parent `Group`s just like a real DOM click, and this bit us twice on the same component.** `MarkPoint`'s `onMouseDown` selects a point, but `Mark` (which contains it) sits inside `MarkImage`'s outer `Group`, whose own `onClick` treats any plain left click as "clicked the background" and calls `clearSelectedPoints`. Konva fires `mousedown` → (on release) a synthesized `click` that bubbles through every ancestor Group same as the DOM would. So mousedown selects, then the very same physical click's bubbled `click` on the ancestor immediately deselects. This makes the bug look intermittent rather than 100% broken: Konva suppresses the synthetic `click` when a drag exceeds `Konva.dragDistance` (default 3px), so any click with a little pointer jitter "works" and a perfectly steady click silently fails — exactly the kind of flakiness that's easy to misdiagnose as a timing/race issue instead of event bubbling. Fix: add `onClick={e => { e.cancelBubble = true; }}` on the child that owns the selection gesture. Applies to any Konva node nested inside a Group/Stage that has its own click-driven "deselect" handler — check for this pattern proactively rather than after noticing "clicks sometimes don't work."

## Tailwind / tailwind-merge

- **When manually specifying both a shorthand utility (`border`) and a per-side override (`border-l-0`) in the same class string, `tailwind-merge`'s conflict resolution — not CSS cascade order in the final stylesheet — decides which one wins, and it goes by string order, keeping whichever comes LAST in the template literal.** `border-l-0 ... border` → `border` wins, `border-l-0` is silently dropped (both are treated as members of the same "border-width" conflict group by tailwind-merge, so only the last one survives merging — this happens in JS before any CSS is emitted, not as a cascade/specificity effect). `border ... border-l-0` → the per-side override survives and correctly zeroes just that edge. This is invisible from reading the JSX alone — you have to know tailwind-merge treats these as conflicting and resolves by string position, not by CSS specificity as you'd normally expect from stacking two "different-looking" utility classes. Whenever combining a shorthand with a per-side variant of the same property via `cn()`/`twMerge`, put the more specific one LAST, and leave a comment — it's exactly the kind of thing a later "cleanup" pass would silently break by reordering.
